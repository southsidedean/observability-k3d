# Plan: a home network operations center on k3d, with AI agents

Status: planning (2026-10-27). Nothing below is built yet. The current repository (the
`scripts/cluster-setup-k3d-observability-everything.sh` stack) keeps working until step 10
replaces it.

## Goal

NOC-level monitoring and alerting for a home network that anyone can build from the docs.
You know when something on your network breaks, before anyone in the house tells you.
Alerts reach your phone. Every device, link, and service shows on one board, with the logs
behind it. You get one sign-in for every page, and agents that can read all of it and help
explain what went wrong.

The repository holds no one's own setup. Your settings and secrets live in two files that
are never committed, and the repository carries a commented example of each.

## What went wrong last time

A review on 2026-10-27 found that the old stack collected metrics but couldn't tell anyone
about a problem. Each of these is fixed by a step below:

- Alerts went nowhere: Alertmanager had no receivers, and Grafana's contact points were off.
- The UniFi alert rules queried metric names unpoller doesn't export (`unifi_device_*`
  instead of `unpoller_device_*`, and percentages instead of 0 to 1 ratios), so they could
  never fire.
- The ping and website probes were never scraped (missing the chart's `release` label), and
  the blackbox exporter had no `icmp` module and no permission to ping.
- Syslog never arrived. The Promtail in loki-stack only reads RFC5424, rsyslog sends
  RFC3164 by default, and UniFi sends syslog only over UDP while the stack listened only on
  TCP.
- k3s doesn't expose the scheduler, controller-manager, etcd, or kube-proxy metrics, so the
  chart's alerts for them would have fired forever.
- Prometheus's host-folder volume was removed (commit `2e1b018`), so a redeploy would lose
  its history.
- The kagent UI was open to the whole network with no login, with an OpenAI key behind it.

## Decisions

| Question | Decision |
|---|---|
| Where it runs | One k3d cluster of its own on one Linux server, separate from anything else running there. The cluster's name, ports, and Docker network come from `settings.yaml`, so it can sit next to other k3d clusters. |
| Standalone | Nothing here depends on another project. Other stacks' exporters (node-exporter, GPU, Plex, SMART) can be listed as scrape targets like any device, but the NOC never reads another stack's Prometheus and never shares config, code, or services with it. |
| The cluster is disposable, the data isn't | Upgrading means deleting the cluster and creating it again with newer versions. Everything stateful lives in host folders under one data root, so a new cluster picks up where the old one left off. This worked well with the old stack and stays the core rule. |
| How it's deployed | One umbrella Helm chart for everything, with pinned dependencies. `scripts/cluster.sh create` once, then `scripts/deploy.sh` (a plain `helm upgrade --install`) as often as you like. Deploying never deletes the cluster; `scripts/cluster.sh delete` is a separate, deliberate command. |
| Your settings | `settings.yaml` holds every non-secret setting and `.env` holds every secret. Both are gitignored, and `settings.example.yaml` and `.env.example` are committed with a comment on every line. `chart/values.yaml` holds the defaults; you never edit it. `vars.sh` is retired. |
| Nodes | One k3s server and no agent nodes. That uses less memory, kagent's sandbox folder must be on the server anyway, and every host-folder volume lands on the one node. |
| Metrics | kube-prometheus-stack, pinned, with the k3s control-plane scrapes and rules turned off. |
| Logs | The `loki` chart in single-binary mode with retention on, and Grafana Alloy collecting pod logs and syslog. loki-stack and Promtail are retired (both deprecated). |
| Syslog | Alloy listens for both RFC3164 and RFC5424, over UDP and TCP, on a LoadBalancer Service published by k3d. It doesn't go through the gateway. |
| Devices | One `devices.yaml` (gitignored, with a committed example) lists every device: name, address, role, and which checks apply. Probes, scrape targets, and the status board are generated from it, so adding a device takes one line. |
| Alerts | Alertmanager sends to ntfy and email. Critical alerts repeat more often than warnings. When the internet link or the router is down, alerts for everything behind it are held back. Alertmanager's always-firing Watchdog alert pings an outside dead man's switch, such as healthchecks.io, so you hear about it when the NOC itself goes down. |
| North/south: agentgateway (decided 2026-10-27) | agentgateway, in standalone mode (its own config file, generated by the chart into a ConfigMap), is the gateway for everything coming into the cluster or leaving it: the only way into the web pages, the only route to the AI model, and the place MCP tools are served from. It starts the trace for each request. Something else is used only where agentgateway can't do the job: syslog over UDP has its own Service. kgateway is retired. |
| East/west: Istio ambient (decided 2026-10-27) | Open-source Istio in ambient mode is the data plane between workloads. ztunnel gives every pod in the mesh mutual TLS and a workload identity, and AuthorizationPolicies use that identity alongside the NetworkPolicies. Istio's waypoint proxies go only where layer-7 metrics or spans are wanted. No sidecars. |
| Traces | Tempo keeps the traces (7 days by default), with Alloy as the OpenTelemetry collector for agentgateway, the waypoints, and kagent. Grafana links traces, logs, and metrics to each other, and Tempo's service graph and request metrics go to Prometheus. |
| Certificates | Two paths, both through cert-manager, picked with `tls.mode` in settings. **Self-issued is the default** (decided 2026-10-27): the stack makes its own certificate authority and issues one wildcard certificate for `*.<domain>`. The authority's key lives in the data root and is restored on each new cluster, so devices that trust it keep trusting it. A page serves the authority's certificate for download, and the docs show how to trust it on each kind of device. **Public certificates from Let's Encrypt** come later (step 11). Changing paths changes only the issuer. |
| Names | Each page gets its own name under one domain (`grafana.<domain>`, `auth.<domain>`, `agents.<domain>`, ...). Subdomains avoid Grafana's sub-path problems. With self-issued certificates the default domain is `noc.home.arpa` (`home.arpa` is reserved for home networks), and the names come from a local DNS record on your router or local DNS server. Public certificates need a domain you own. |
| Sign-in | Authelia as the identity provider (users in a file to start, with LLDAP as a later option), and agentgateway as the OIDC client in front of every page. The gateway passes the signed-in user on in trusted headers and strips the token. NetworkPolicies let only the gateway reach the apps. agentgateway's OIDC client can't trust a private certificate authority, so the gateway reaches Authelia inside the cluster over HTTP, with the forwarded headers set so Authelia computes a consistent https issuer. Tokens are checked against a local copy of Authelia's keys (the offline setup kia's proof of concept used). With public certificates, the gateway can use OIDC discovery instead. |
| Releases | Development and testing happen on a test VM. `main` is tested there, and production runs the latest release, tagged with a CHANGELOG entry. Deploying a release means recreating the cluster from that tag. |
| Name and logo (decided 2026-10-27) | **ok3d**, short for observability-k3d, the way kia is short for kodi-iptv-assistant: the name in the docs, on the pages, and on commands (`ok3d doctor`). It's also the cluster's default name. Its mark is kia's screen and stand with an amber pulse line over a row of device tiles, in kia's colors and on kia's grid (`images/ok3d-logo.svg`, and `ok3d-logo-dark.svg` for dark mode). The repository keeps its name. |
| Grafana's sign-in | Grafana trusts the gateway's user header, and Authelia groups map to Grafana roles (admins are Admin, everyone else is Viewer). |
| Agents | kagent 1.0 (Agent Substrate), pinned. Until GA, the newest 1.0 alpha. Its tools are read-only: Prometheus, Loki, and Alertmanager queries, over MCP, through the gateway. It gets read-only Kubernetes access to `monitoring` and `agents`, and never Secrets. Agents hold no model key; the gateway adds it. The built-in bash and file tools are off unless an agent needs them. Prompt caching is on. |
| Model | Claude, through the gateway, with its own API key and a monthly spend limit. Other providers can be configured through the gateway. |
| What the agents never do | Change anything: no restarts, no silences, no config changes. They read, explain, and suggest. |

## The data root

One folder on the server, set by `host.dataRoot`. A dedicated filesystem is best. The
install doc shows how to make one with LVM, and how to grow it later.

```text
<host.dataRoot>/
├── prometheus/      the time series database
├── alertmanager/    silences and what was already sent, so a new cluster doesn't repeat alerts
├── loki/            logs
├── tempo/           traces
├── grafana/         Grafana's database: users' stars, edited dashboards, preferences
├── authelia/        its database (sessions, second factors); users.yml stays in your settings
├── certs/           the certificate authority (self-issued), or the ACME account key and the
│                    certificate (public), restored into each new cluster
├── kagent/          kagent's database
└── kagent-ate/      kagent's sandbox state, mounted at /var/lib/ate on the server node
```

`scripts/check-host.sh` creates any missing folder with the owner and mode its app runs as.
No folder is world-writable. Before an upgrade, `scripts/backup.sh` copies `grafana/` and
`authelia/`, the two that migrate forward only.

## The host

What the server needs, and what `scripts/check-host.sh` checks before anything is created:

- Linux with Docker, k3d 5.9 or newer, Helm, and kubectl. kagent 1.0 needs Kubernetes 1.37
  (pod certificates), and k3d 5.9 can run `rancher/k3s:v1.37.x`.
- About 11 GiB of free memory for everything (kagent's node alone measured 1.7 GiB at rest;
  the mesh and Tempo add about 1 GiB), and about 7 GiB with agents off
  (`agents.enabled: false`).
- An x86-64-v2 processor or newer. Some images need more, and the check names any that won't
  run on this processor.
- inotify limits of at least 1024 instances and 1M watches (two k3d clusters on one host
  exhaust the defaults). The check prints the `sysctl` lines to add.
- The data root, on a filesystem that isn't overlay.
- Local DNS you can add records to (most routers can), for the stack's names.

## GitHub, tests, and releases

Set up the way kia's repository is (decided 2026-10-27).

**The repository's settings**

- Squash merges only, with the pull request's title as the commit's title, and branches
  deleted after merging.
- A ruleset for `main`: changes only through a pull request, no force-pushes, no deletion,
  and the checks below required.
- A ruleset for release tags (`v*`): no deletion, no moving, no rewriting.
- Dependabot security updates, private vulnerability reporting, and secret scanning with
  push protection on. The wiki off; the docs live in the repository.

**Workflows** (actions pinned to exact commits, least-privilege permissions, checked by
zizmor):

| Workflow | When | What |
|---|---|---|
| `tests` | every push and pull request, and weekly | **lint and security checks**: shellcheck, zizmor, `helm lint`, kubeconform on the rendered chart, the values schema, JSON and dashboard checks, the privacy check. **chart tests**: helm-unittest for what the chart renders (NetworkPolicies, RBAC, the settings that must refuse to render). **alert rules**: `promtool check rules` and `promtool test rules` for every rule, `amtool check-config` for the routing. **scripts**: the shell scripts' tests, with stand-ins for docker, k3d, and kubectl, under dash and macOS's sh. **end-to-end smoke test**: a k3d cluster on the runner, the chart deployed with agents off, then `scripts/test-monitoring.sh` (targets up, a rule fires, Alertmanager routes it to a test receiver, a syslog line in each format reaches Loki, sign-in redirects). |
| `upstream` | weekly | Whether the pinned charts and images have newer releases, and whether the vendored dashboards have newer revisions. Opens an issue, never a change. |
| `images` and `image scan` | when the repository builds its own images (the MCP servers, step 8 on) | Build, Trivy scan before pushing (no fixable high or critical CVEs), push, attest provenance, and scan the published images weekly. |
| `release` | a merge to `main` that changes the version | Tags the release and publishes its notes from `CHANGELOG.md`. |

Dependabot updates the actions monthly, grouped into one pull request, for releases at
least a week old.

**Files:** `LICENSE`, `SECURITY.md` (how to report a problem privately, and how the stack
limits the damage), `CONTRIBUTING.md` (branches, hooks, checks, releases),
`CHANGELOG.md`, a pull request template with its checklist, and issue templates for bugs
and features, with links to troubleshooting and private security reports.

**Git hooks** (`git config core.hooksPath .githooks`): pre-commit refuses commits on `main`,
of anyone's own settings files, of secrets, and of private names or addresses outside the
examples. Pre-push runs the quick checks.

**Testing before a release:** CI covers what a runner can. Each release is also deployed on
a test VM from scratch, with agents on and the self-issued certificates trusted in a
browser, before production moves to it.

## Steps

Each step ends with something that works on its own and a test that proves it.

1. **Groundwork.** The chart skeleton, `settings.example.yaml`, `.env.example`,
   `scripts/env.sh` (reads both, fails with a clear message on a missing or bad value), and a
   values schema so a typo is refused at deploy time. `.gitignore` covers `settings.yaml`,
   `.env`, `devices.yaml`, and `users.yml`. Git hooks refuse commits of those files, of
   anything that looks like a secret, and of private addresses or host names outside the
   examples. The GitHub setup below, with the repository's settings and rulesets applied
   first, so every later step goes through a pull request and its checks.
2. **The host and the cluster.** `scripts/check-host.sh` and `scripts/cluster.sh
   create|delete`: one server node, the data root mounted into it, kagent's sandbox folder,
   and only the published ports in settings (web, syslog). The Kubernetes API listens only on
   127.0.0.1.
3. **Metrics.** kube-prometheus-stack with persistent volumes bound to the data root's
   folders by label, the k3s scrapes off, the blackbox exporter with an `icmp` module and
   `NET_RAW`, and unpoller with its per-client app (DPI) metrics off by default. Probes and
   scrape targets are generated from `devices.yaml`. Test: every target in `devices.yaml`
   shows as up or down, and nothing is missing.
4. **Alerts reach you.** Alertmanager to ntfy and email, the routing and holding back, and the
   dead man's switch. Rules for devices (down, flapping), the internet link (down, packet
   loss, latency, DNS), hosts (disk with `predict_linear`, memory, temperature, RAID, SMART),
   UniFi (device offline, port errors, client experience), the UPS (on battery, low battery),
   certificates (expiring), and the NOC itself. Each alert links to a runbook in
   `docs/runbooks/`. `promtool test rules` covers every rule, and `amtool` checks the
   routing. Test: `scripts/test-monitoring.sh --send-test-alert` reaches your phone.
5. **Logs.** Loki with retention, and Alloy's pod logs and syslog (both formats, UDP and
   TCP). Labels for host, app, and severity. Ready configs for UniFi, rsyslog, and Alloy on a
   Linux host. Log-based alerts (SSH brute force, sudo failures, UniFi IPS events). Test: a
   message sent in each format, over each transport, shows up in Grafana.
6. **The front door.** cert-manager with the stack's own certificate authority, kept in the
   data root, and a page to download it. agentgateway with TLS, the security headers, and
   routes to Grafana, Prometheus, Alertmanager, and Authelia. Authelia with one admin account. OIDC at the gateway, the user headers, and
   Grafana's role mapping. NetworkPolicies so only the gateway reaches the apps. Test:
   signed out, every page redirects to sign-in; signed in, every page loads, once.
7. **Mesh and traces.** Istio ambient (istiod, istio-cni with k3d's platform setting, and
   ztunnel) on `monitoring`, `gateway`, and `auth`, with mutual TLS required. Waypoints only
   where layer-7 metrics or spans are wanted. AuthorizationPolicies by workload identity,
   next to the NetworkPolicies (which now allow the mesh's port, 15008). Tempo, with Alloy
   as the OpenTelemetry collector for the waypoints and agentgateway. Grafana links traces,
   logs, and metrics to each other, and Tempo's service graph and request metrics go to
   Prometheus. Test: a signed-in page load shows as one trace from the gateway to the app,
   and a pod outside the mesh can't reach an app inside it.
8. **Agents.** kagent 1.0 behind the front door at `agents.<domain>`. The model route and the
   MCP tools on the gateway. Read-only RBAC. NetworkPolicies so the sandboxes can reach only
   the gateway (not kagent's control plane, which trusts a plain identity header). The first
   agent explains a firing alert: what changed, what the logs say around it, and what to
   check. Alertmanager can send it each new critical alert, and its answer lands next to the
   alert. Each conversation shows as a trace: the agent, the gateway, the model call, and
   each tool call. The `agents` namespace joins the mesh once gVisor sandboxes are proven to
   work with ambient's traffic redirection. Test: a planted instruction in a log line doesn't
   change what the agent does.
9. **The NOC board.** A status board built for this stack: every device from `devices.yaml`
   as a tile (up, degraded, down), the internet link, active alerts, and recent changes. The
   UniFi dashboards are vendored at a pinned revision, with local edits kept as patches
   applied on top, so updating never loses them. `scripts/doctor.sh` lists what's wrong in
   plain words.
10. **Retire the old stack.** Remove `vars.sh`, the old setup script, kgateway, loki-stack,
   and the old manifests. An upgrade doc for anyone on the old layout covers which data
   carries over: Grafana's database and Prometheus's history do, and old Loki data does
   not (the storage format changed).
11. **Public certificates.** `tls.mode: public`: Let's Encrypt through cert-manager with a
    DNS-01 challenge, so nothing has to be reachable from the internet, using Let's
    Encrypt's staging server until you switch to production. If cert-manager supports your
    DNS provider (Cloudflare, Route53, Google, Azure, DigitalOcean, RFC2136, and others), it
    updates your zone directly. If not (cPanel hosting and many registrars), you add one
    CNAME at your provider, `_acme-challenge.<domain>`, pointing into a zone at a supported
    provider, and cert-manager follows it (`cnameStrategy: Follow`); the cluster's key can
    then edit only that zone, never your real DNS, email, or website. The certificate and
    the ACME account key are kept in the data root and restored on each new cluster, so
    recreating it doesn't hit Let's Encrypt's rate limits. The docs check for CAA records
    that would block Let's Encrypt. Test: on the test VM first, then in production.

## To check before building

- agentgateway: does it reload a renewed certificate when the mounted Secret changes, or does
  it need a restart (step 6)?
- cert-manager: does a restored certificate authority Secret keep issuing from the same
  authority (step 6)? Does it adopt a restored Let's Encrypt certificate without issuing
  again? Test that against staging, keeping the annotations it writes (step 11).
- agentgateway with Authelia inside the cluster: does the token exchange need its own
  listener to set the forwarded headers, as in kia's proof of concept? How does the local
  copy of Authelia's keys get refreshed when they rotate (step 6)?
- cert-manager: the CNAME-delegated challenge end to end, with a wildcard and the bare name
  in one certificate, both validated through the one delegated `_acme-challenge` name
  (step 11).
- Alloy: the minimum version that reads RFC3164 syslog, and how it labels UniFi's messages
  (step 5).
- Grafana: mapping a role from a gateway header, or Grafana's own OIDC against Authelia if
  the header can't carry the role (step 6).
- kagent 1.0: the GA version, and whether GA changes the install or the resources (step 8).
- Istio ambient on k3d: the install with k3d's platform setting, ztunnel and istio-cni
  with k3s's CNI paths, and the NetworkPolicies with the mesh's port (step 7).
- Istio ambient and kagent's gVisor sandboxes: does ambient's traffic redirection inside
  the pod catch traffic from gVisor's own network stack? Until it's proven, `agents` stays
  out of the mesh (step 8).
- agentgateway listeners: confirm there's no UDP listener, which is why syslog has its own
  Service (step 5).
- unpoller: how many series a typical home produces with DPI on and off, to set the default
  (step 3).
